0.1 — Competitive teardown
1.1Set up the repo and ADR log
Private GitHub repo, MIT-incompatible license header decided, and docs/decisions/ with 0001-gutenberg-not-a-page-builder.md written in ADR format. Every architectural decision from here gets a numbered file. This is how the project stays resumable if you step away.
1.2Benchmark six competitor demo sites
Woodmart, Porto, Flatsome, Blocksy, Kadence Shop, Shoptimizer. Run Lighthouse mobile on each shop archive and one product page. Record LCP, TBT, CLS, CSS transfer bytes, JS transfer bytes, request count, and whether jQuery loads.
1.3Benchmark the floor
Same measurements on a stock Twenty Twenty-Five install with WooCommerce and no other plugins. This is the theoretical best case and tells you how much headroom you actually have.
1.4Write docs/benchmarks.md
The table from 1.2 and 1.3, dated. Re-run it quarterly. This file eventually becomes the comparison chart on your sales page, so record methodology precisely enough to reproduce.
1.5Feature frequency audit
List every commerce feature across the six themes and score how many have it. Anything present in five or more is table stakes and belongs in v1.0 regardless of how you feel about it.
1.6Reconcile against the v1.0 ledger
Compare the audit to the planned v1.0 feature list. If something scored 5+ and is not in v1.0, either move it in or write an ADR explaining the omission.
0.2 — Design token system
2.1Write tokens.json
Use the shape in the appendix. Resist adding a token you cannot name a concrete use for. Every unused token becomes dead weight in three output formats.
2.2Decide the responsive contract now
Document which token categories are responsive and which are fixed. Spacing and type size are responsive; color and radius are not. Writing this down now prevents an inconsistent control API in Phase 2.
2.3Build the token compiler
A Node script that reads tokens.json and emits three artefacts: theme.json settings, a CSS custom-property stylesheet, and a TypeScript module of control defaults. Run it as a build step, never by hand.
2.4Snapshot-test the compiler
Commit expected output for all three targets. A token change should show up as a readable diff in review, which is the only way you will catch an accidental palette change later.

0.5 — Seed data
5.1Write the seed generator
A WP-CLI command producing 5,000 products: 40% variable with three attributes and roughly twelve variations each, 60% simple. Realistic titles, prices, stock states, categories, and reviews.
5.2Generate real images
Do not use a placeholder service. Generate and attach actual images at realistic dimensions with all WordPress sizes registered, so image handling is measured honestly.
5.3Export a restorable snapshot
Dump to SQL plus a media tarball, committed via Git LFS or cached in CI. Regenerating on every CI run is far too slow; restore in under thirty seconds.
5.4Document the reset procedure
A single command that wipes local, restores the snapshot, and leaves you on a working shop. You will run this hundreds of times.
0.6 — The pipeline
6.1Static analysis job
PHPCS, PHPStan, ESLint, and tsc as four distinct steps so a failure names itself. Target under three minutes.
6.2Playwright harness
Config pointing at wp-env, with the no-jQuery spec from the appendix as your first test. Add a smoke test that loads shop, product, cart, and account without console errors.
6.3Lighthouse CI with assertions
Use the appendix lighthouserc.js. Three runs per URL to smooth variance. Verify the numbers are stable across runs before trusting the thresholds.
6.4Bundle size limits
size-limit or bundlesize on every built JS and CSS entry point, with per-entry budgets that sum to the totals in the roadmap.
6.5Branch protection
Require every check on main. No direct pushes, including yours. Working solo makes this more important, not less, because there is nobody else to catch it.
6.6Prove the gate fails
Commit a 200KB stylesheet of junk and a script that blocks the main thread for 400ms. Confirm the build goes red on the byte assertion and on total blocking time. Screenshot it, then revert.
6.7Write docs/performance-budget.md
The numbers, where each is enforced, and the rule that the budget is never relaxed to accommodate a feature. Features that do not fit load on demand or do not ship.

The jQuery assertion
Lighthouse will not catch this on its own. Make it an explicit Playwright test that runs on every page you render.

// tests/e2e/no-jquery.spec.ts
import { test, expect } from '@playwright/test';

const pages = ['/', '/shop/', '/cart/', '/my-account/'];

for (const path of pages) {
  test(`no jQuery on ${path}`, async ({ page }) => {
    await page.goto(path);
    const found = await page.evaluate(
      () => typeof (window as any).jQuery !== 'undefined'
    );
    expect(found, `jQuery loaded on ${path}`).toBe(false);
  });
}
.github/workflows/ci.yml — skeleton
name: CI
on: [push, pull_request]

jobs:
  static:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with: { php-version: '8.2', tools: composer }
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: composer install --no-progress
      - run: pnpm install --frozen-lockfile
      - run: composer run phpcs
      - run: composer run phpstan
      - run: pnpm run lint
      - run: pnpm run typecheck

  perf:
    runs-on: ubuntu-latest
    needs: static
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm run build
      - run: pnpm wp-env start
      - run: pnpm run seed:restore     # cached SQL dump, not a live generate
      - run: pnpm exec lhci autorun
      - run: pnpm exec playwright test
Do not skip task 4.6. A gate you have never seen fail is not a gate. Commit a deliberately oversized stylesheet, watch the build go red, then revert. Until you have done that, you do not know the budget is enforced.
